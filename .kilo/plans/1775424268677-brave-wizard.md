# Plan: Modular Question Generator + Validation

## Goal
Refactor question generation so multiple AI providers can be plugged in (Google GenAI/Gemini now, OpenRouter next), use the OpenRouter SDK for the OpenRouter provider, and add strict validation that throws when generated output does not match required quiz rules. Make generation rules configurable while preserving current defaults.

## Current state (observed)
- `src/question/question-generator.ts` has a single concrete class (`QuestionGenerator`) tightly coupled to `@google/genai` and Gemini schema config.
- Prompt contract is embedded as plain text and parsed with provider-specific assumptions.
- Output mapping to `Question` exists, but there is no semantic validation (question count/type/alternatives/correct answer inclusion).
- `src/worker.ts` directly constructs `QuestionGenerator(apiKey, geminiModel)` using `GOOGLE_AI_API_KEY` and `GEMINI_MODEL`.

## Target architecture

### 1) Provider-agnostic generator contract
Introduce a stable interface used by the worker and game flow:
- `IQuestionGenerator` with `generateQuestions(topic: string): Promise<GeneratedQuiz>`.
- Shared types for AI raw payload and final domain output.

### 1.5) Configurable generation rules
Introduce a shared quiz generation config object consumed by prompt builders and validator:
- `totalQuestions`
- `numericQuestionCount`
- `multipleChoiceQuestionCount`
- `multipleChoiceAlternativeCount`
- `quizNameMaxLength`

Default values must match current behavior:
- `totalQuestions = 5`
- `numericQuestionCount = 2`
- `multipleChoiceQuestionCount = 3`
- `multipleChoiceAlternativeCount = 4`
- `quizNameMaxLength = 40`

Validation rule: `numericQuestionCount + multipleChoiceQuestionCount === totalQuestions`.

### 2) Separate provider implementations
Create separate classes:
- `GeminiQuestionGenerator` (migrated from current implementation, behavior preserved).
- `OpenRouterQuestionGenerator` (SDK-based implementation using the OpenRouter client).

Provider-specific prompt transport/parsing should stay inside provider classes.

### 3) Factory-based selection
Add a factory to select implementation from env config:
- `QUESTION_GENERATOR_PROVIDER` (e.g. `gemini` or `openrouter`).
- Existing Gemini envs remain supported.
- OpenRouter envs added (key + model + optional base URL).

### 4) Validation layer (strict, fail-fast)
Add a validator that enforces the prompt contract before returning quiz:
- Exactly `totalQuestions` questions total.
- Exactly `numericQuestionCount` numeric questions: `alternativeAnswers` empty, `correctAnswer` positive integer.
- Exactly `multipleChoiceQuestionCount` multiple-choice questions: exactly `multipleChoiceAlternativeCount` alternatives, includes `correctAnswer`, and wrong options are not positive integers.
- Question text and correct answer must be non-empty strings.
- `quizName` non-empty and max `quizNameMaxLength` chars.

If any rule fails: throw descriptive error with field-level details.

## OpenRouter implementation details
- Use the OpenRouter SDK client with `OPENROUTER_API_KEY`.
- Configure model via `OPENROUTER_MODEL`.
- Provide messages (system + user) with explicit JSON-only instruction.
- Build prompt text from shared generation config so requested counts are dynamic.
- Parse assistant content to JSON and map to internal raw quiz object.
- Keep optional `OPENROUTER_BASE_URL` only if the SDK supports custom base URL in this runtime; otherwise omit it to avoid unsupported configuration.

Note: even with SDK usage, OpenRouter does not guarantee schema enforcement like Gemini responseSchema, so validator remains the hard safety gate.

## Validation behavior design
- Build validator against parsed raw object (before mapping to domain `Question`) and apply the shared config.
- Return a normalized, safe shape if valid; otherwise throw `QuestionValidationError` with an array of issues.
- Keep errors deterministic and actionable, example:
  - `questions[3].alternativeAnswers must contain exactly 4 items`
  - `questions[1].correctAnswer must be a positive integer for numeric question`

## Integration flow after refactor
1. Worker resolves generation config (defaults + optional env overrides + sanity checks).
2. Worker chooses provider via factory.
3. Provider generates raw JSON text and parses raw quiz.
4. Validator checks config-driven rules and throws on mismatch.
5. Valid quiz maps to existing `Question` domain objects and returns.
6. Worker proceeds unchanged with Durable Object creation.

## Implementation sequence
1. Extract shared types + interface from current generator.
2. Add `quiz-generation-config` with defaults matching current behavior.
3. Move existing Gemini logic into `gemini-question-generator.ts` with parity behavior and config-driven prompt.
4. Add config-aware validator and invoke it in Gemini path.
5. Implement OpenRouter generator (SDK) and reuse same config-driven validator + mapper.
6. Add factory and update worker to use it.
7. Update env typings and defaults.
8. Add tests for validator/config behavior and provider-independent contract.

## Test plan
- Unit tests for validator (`src/question/question-validator.spec.ts`):
  - valid mixed quiz passes.
  - wrong total question count fails.
  - wrong numeric/multiple split fails.
  - missing/extra alternatives fails.
  - `correctAnswer` not in alternatives fails.
  - wrong answers containing positive integers in MC fails.
  - quiz name > configured max fails.
- Unit tests for config defaults/normalization (`src/question/quiz-generation-config.spec.ts`):
  - defaults equal current behavior.
  - override values applied correctly.
  - invalid combinations (sum mismatch, non-positive counts) throw clear errors.
- Optional provider tests:
  - mock Gemini/OpenRouter raw responses and assert validation + mapping behavior.

## Backward compatibility
- Default provider remains Gemini if `QUESTION_GENERATOR_PROVIDER` is unset. (Confirmed)
- Existing env vars continue working.
- New generation-rule env vars are optional; omitting them preserves current behavior.
- Worker API surface remains unchanged.

## Future-proofing for self-correction phase
- Keep validator errors structured (`issues: string[]`) so a follow-up “repair prompt” step can feed these issues back into AI.
- Future extension point:
  - `generate -> validate -> if invalid then repair -> validate -> return/throw`.

## Risks and mitigations
- **Risk:** OpenRouter returns wrapped markdown/non-JSON text.
  - **Mitigation:** strict JSON instructions + robust parsing guards + explicit parse error.
- **Risk:** SDK/runtime mismatch in Cloudflare Worker environment.
  - **Mitigation:** use SDK path that is fetch-compatible in Workers; if SDK feature is unavailable, limit usage to supported client initialization and request methods.
- **Risk:** provider-specific drift in output fields.
  - **Mitigation:** central validator + shared mapper.
- **Risk:** runtime misconfiguration.
  - **Mitigation:** factory throws clear errors for missing provider env values.

## Acceptance criteria
- Worker can switch between Gemini and OpenRouter by env config only.
- Question generation rules are configurable via central config/env.
- If no new config is provided, behavior remains exactly as today (5 total, 2 numeric, 3 MC, 4 alternatives, max name 40).
- Invalid generated quiz throws validation error before game creation.
- Existing behavior preserved for valid quizzes.
- Validator test suite covers contract rules and is green.
